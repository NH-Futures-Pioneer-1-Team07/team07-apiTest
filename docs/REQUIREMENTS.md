# API 시나리오 테스트·모니터링 서비스 요구사항

## 1. 배경과 목표

AI로 백엔드 API가 빠르게 만들어지지만, 그 API가 **사용자 입장에서 의도대로 동작하는지** 검증하는 단계가 병목이 된다.
유닛 테스트는 테스트 코드를 다시 읽어야 하므로 또 다른 병목이 될 수 있다.

이 서비스는 프론트엔드 E2E 테스트처럼 **실제 API를 실제 데이터로 호출**해서 검증하고, 그 결과를 화면에서 바로 확인할 수 있게 한다.

검증 대상 오류 유형:

| 유형 | 예시 |
| --- | --- |
| 단일 API 오동작 | 필수값 누락인데 성공 응답, 응답 필드 누락·타입 불일치 |
| 시간대 의존 오류 | 주간/야간 장 시간에만 동작하는 API, 장 마감 직후 오류 |
| 흐름(시나리오) 오류 | 신규주문 → 정정 → 취소 → 주문내역 조회 중 뒤 단계에서 실패 |
| 지속 모니터링 | 같은 케이스를 주기적으로 돌려 성공률 추이와 회귀 감지 |

## 2. 범위

### 2.1 이번 단계 (MVP)

- 대상: **NH선물 API** 49개 (HTTP 41, WebSocket 8)
- API 목록 입력: `pioneer-1st-code-team07/docs/nh-api/apis/*.md` 파싱
- 테스트 케이스 작성: Claude 채팅에서 요청해 생성, 레포에 파일로 저장
- 실행 환경: 로컬 실행, **모의 도메인(`apidemo.futures.co.kr`)만 사용**

### 2.2 이후 단계 (확장)

- Swagger/OpenAPI URL 입력으로 API 목록 가져오기
- 엑셀(.xlsx) 파일 드래그앤드롭·파일 선택 업로드
- 다른 서비스·기업 API 대상 프로젝트(멀티 프로젝트)
- DB 저장, 서버 배포, 스케줄 실행, 알림

MVP부터 **API 목록 입력을 "소스 어댑터" 구조로 분리**해 두어, MD·Swagger·엑셀이 모두 같은 내부 API 모델로 변환되게 한다.

## 3. 핵심 개념 (도메인 모델)

| 개념 | 설명 |
| --- | --- |
| Project | 테스트 대상 서비스 단위. MVP는 `nh-futures` 하나 |
| Environment | 대상 도메인·인증정보 묶음. 예: 모의, 실전 |
| API | 메서드, URL, 통신 방식(HTTP/WS), 요청 제한 유형, INPUT/OUTPUT 필드 정의 |
| TestCase | 1개 이상의 Step과 판정 규칙의 묶음. 단일 API 케이스 = Step 1개 |
| Step | API 1회 호출. 요청 데이터, 기대 응답, 이전 Step 응답에서 꺼낼 변수 |
| Run | TestCase 1회 실행 기록. 상태·시작/종료 시각·Step별 요청/응답 원문 |
| Issue | 제보 건. 현상, 대상 API, 제보 상태, NH 답변, 결론, 사용 규칙, 연결된 케이스 |
| SpecOverride | 명세 보정. 명세와 실제 동작이 다르지만 NH가 실제 동작이 맞다고 확인한 항목 (예: `expires_in` Number). 반드시 Issue에 연결 |
| ReferenceData | 테스트 입력에 쓰는 기준 데이터. 종목 마스터, 거래소별 장 운영 시간, 현재가 같은 실행 시점 값 |

### 4.2 테스트 케이스

| ID | 요구사항 | 단계 |
| --- | --- | --- |
| F-TC-1 | 테스트 케이스는 **선언형 파일(YAML 또는 JSON)** 로 레포에 저장한다. Claude가 작성·수정하고 사람이 diff로 검토할 수 있어야 한다 | MVP |
| F-TC-2 | 단일 API 케이스: 정상값, 필수값 누락, 경계값(길이 초과·0·음수), 잘못된 코드값, 잘못된 타입, 인증 없음/만료 토큰 | MVP |
| F-TC-3 | 시나리오 케이스: 여러 Step을 순서대로 실행하고, 앞 Step 응답 값을 변수로 꺼내 뒤 Step 요청에 넣는다 (예: `ord_no`) | MVP |
| F-TC-4 | 정리(cleanup) Step: 성공·실패와 관계없이 마지막에 실행해 남은 주문 취소 등 상태를 되돌린다 | MVP |
| F-TC-5 | 실행 시간대 조건: 케이스별로 실행 가능한 시간대(주간장, 야간장, 장외)를 지정하고, 조건 밖이면 `건너뜀`으로 기록한다 | MVP |
| F-TC-6 | 케이스 파일 스키마 검증: 존재하지 않는 API, 정의되지 않은 필드, 정의되지 않은 변수를 실행 전에 오류로 알린다 | MVP |
| F-TC-7 | 케이스에 태그(예: `주문`, `시세`, `야간`, `negative`)를 달아 필터·일괄 실행한다 | MVP |
| F-TC-8 | 매개변수 반복: 같은 케이스를 값 목록으로 돌린다 (예: `req_qty` 1000, 2000, 2001, 9999). 근거 NH-001 | MVP |
| F-TC-9 | 선택 항목은 "키 생략", "빈 문자열", "올바른 값" 세 경우를 구분해서 만든다. 기본 요청은 키 생략. 근거 NH-013 | MVP |
| F-TC-10 | 반복 Step: 응답 값이 조건을 만족할 때까지 같은 API를 다시 호출한다. 두 가지 용도: 페이지 넘기기(`nxt_key` 를 다음 요청에 넣고 종료 조건까지), 상태 대기(주문 상태가 접수·체결·거부가 될 때까지, 최대 대기 시간 지정). 근거 NH-005, NH-011 | MVP |
| F-TC-11 | 기준 데이터 참조: 종목 마스터에서 종목코드·거래소 코드를 가져오고, 현재가 조회 결과로 주문 가격을 계산해서 요청에 넣는다. 근거 NH-004 | MVP |
| F-TC-12 | 거래소별 장 운영 시간표로 실행 시간대 조건을 판단한다 (국내 주간·야간, CME 휴장, 모의 해외 주문 07:00~24:00). 근거 NH-009 | MVP |
| F-TC-13 | 회귀 케이스: 제보 건마다 재현 케이스 1개를 두고 `issue: NH-00X` 를 붙인다. 기대값은 NH가 설명한 현재 동작이다 | MVP |

시나리오 예시 (국내 주문 흐름):

1. `token` 발급
2. `domestic_deposit` 예수금 조회
3. `domestic_orderable-quantity` 주문가능수량 조회
4. `domestic_order` 지정가 신규주문 → `ord_no` 저장
5. `domestic_order-history` 에서 `ord_no` 존재 확인
6. `domestic_modify` 가격 정정
7. `domestic_cancel` 취소
8. `domestic_order-history` 에서 취소 상태 확인
9. (cleanup) 미체결 주문이 남아 있으면 취소

### 4.3 판정 규칙 (Assertion)

| ID | 요구사항 |
| --- | --- |
| F-AS-1 | HTTP 상태 코드 일치 |
| F-AS-2 | 응답 스키마: OUTPUT 정의의 필드 존재 여부, 타입, 길이 |
| F-AS-3 | 필드 값 규칙: 같음, 포함, 정규식, 범위, 비어있지 않음, 코드값 목록 중 하나 |
| F-AS-4 | 업무 메시지 코드: `msg_cd`, `errorCode` 가 기대값인지. 오류코드 정의서(122행)와 연결해 의미를 표시한다 |
| F-AS-5 | 응답 시간 상한 (예: 3초 초과 시 실패) |
| F-AS-6 | Step 간 일관성: 앞 Step에서 만든 데이터가 뒤 조회 결과에 반영되었는지 |
| F-AS-7 | 실패 시 **기대값, 실제값, 어떤 규칙이 왜 실패했는지**를 사람이 읽을 수 있는 문장으로 남긴다 |
| F-AS-8 | 본문 형식: 응답 본문이 비어 있거나 JSON이 아니면 실패로 판정한다 (HTTP 200이어도). 근거 NH-012 |
| F-AS-9 | 엄격한 JSON 타입 비교: 명세가 String인데 숫자가 오면 실패. 명세 보정이 있으면 보정 기준으로 판정하고 보정 사실을 표시한다. 근거 NH-002 |
| F-AS-10 | 배열 건수: 응답 배열 길이, 건수 필드(`nrec`)가 요청 값과 맞는지 (예: 건수 = min(`req_qty`, 상한)). 근거 NH-001 |
| F-AS-11 | 배열 각 행 규칙: 모든 행에 규칙 적용 (예: 저가 ≤ 시가·종가 ≤ 고가). 위반 행 수와 비율, 대표 예시 행을 남긴다. 근거 NH-006 |
| F-AS-12 | 빈 행 감지: HTTP 200인데 행의 주요 필드가 모두 빈 값이면 실패. 근거 NH-004 |
| F-AS-13 | 연속성·중복: 날짜 간격(평일 누락), 페이지 사이 중복 행, 같은 페이지가 반복되는지. 근거 NH-005, NH-006 |
| F-AS-14 | 조건부 규칙: "체결수량 > 0 이면 체결가격 > 0" 처럼 다른 필드 값에 따라 적용 |
| F-AS-15 | 검증 제외 필드: 미사용 필드는 값 검증에서 뺀다 (명세 보정의 한 종류). 근거 NH-003 |
| F-AS-16 | 시간 지표: 응답 시간뿐 아니라 "주문 응답 → 거래소 접수" 처럼 Step 사이 경과 시간에 상한을 둔다. 근거 NH-011 |

### 4.5 테스트 결과 상태

| 상태 | 의미 |
| --- | --- |
| 성공 | 모든 판정 규칙 통과 |
| 실패 | 판정 규칙 중 하나 이상 불일치 (API가 기대와 다르게 동작) |
| 진행중 | 실행 중 |
| 오류 | 테스트 자체를 실행하지 못함 (연결 실패, 케이스 파일 오류) |
| 건너뜀 | 실행 시간대 조건 밖, 또는 앞 Step 실패로 미실행 |

`실패`와 `오류`를 나누어야 "API 버그"와 "테스트 환경 문제"를 구분할 수 있다.
제한 시간 초과는 서버가 응답하지 못한 것이므로 `오류`가 아니라 `실패`(성능)로 본다 (NH-008).

실패 결과에는 제보 연결 표시를 붙인다 (4.6 참고):

| 표시 | 의미 |
| --- | --- |
| 새 실패 | 알려진 제보와 맞지 않음. 제보가 필요한지 검토 |
| 알려진 이슈 | 기존 제보와 같은 현상. 제보 ID와 제보 상태를 함께 표시 |
| 동작 변경 | 회귀 케이스 결과가 NH가 설명한 동작과 달라짐 (고쳐졌거나 바뀜) |

## 5. 화면 요구사항

공통: 좌측 메뉴 4개 — **대시보드 / API 목록 / 테스트 목록 / 제보 내역**
(처음 기획은 3개였으나, 제보 완료 여부를 한곳에서 보기 위해 제보 내역을 추가)

### 5.1 대시보드

- 전체 요약 카드: 전체 N건 / 성공 N건 / 실패 N건 / 진행중 N건 (+ 오류, 건너뜀)
- 최근 실행 기준 성공률과 기간별 추이
- 실패가 많은 API 상위 목록
- 최근 실패한 테스트 목록 (클릭 시 상세로 이동)
- 시간대별(주간/야간/장외) 실패 분포
- 실행 버튼: 전체 실행, 태그별 실행
- 제보 현황: 새 실패(제보 검토 필요) N건, 제보 완료·답변 대기 N건, NH 확인 중 N건

### 5.2 API 목록

- 목록 컬럼: API 명, 문서명, 통신 방식(HTTP/WS), Method, URL, 요청 제한 유형, 케이스 수, 최근 결과
- 필터: 국내/해외, 시세/주문/계좌/인증, HTTP/WS, 최근 결과 상태
- 검색: API 명, URL
- 가져오기 버튼: MVP는 MD 폴더 다시 읽기. 확장 단계에 Swagger URL 입력, 엑셀 업로드 추가

**API 상세**

- 기본 정보, 설명, INPUT/OUTPUT 필드 표, 예제 JSON
- 이 API의 테스트 요약: 전체 N / 성공 N / 실패 N / 진행중 N
- 이 API가 포함된 케이스 목록 (단일 케이스 + 시나리오 케이스)과 최근 실행 내역
- 이 API 실행 버튼
- 이 API의 제보 건과 사용 규칙, 명세 보정 목록

### 5.3 테스트 목록

- 목록 컬럼: 케이스 이름, 유형(단일/시나리오), 대상 API, 태그, 최근 상태, 최근 실행 시각, 소요 시간
- 필터: 상태, 유형, API, 태그, 기간

**테스트 상세**

- 상단: 상태 배지 (성공/실패/진행중/오류/건너뜀), 실행 시각, 소요 시간, 환경
- 실패 시 상단 요약: **기대한 응답**, **실제 응답**, **어떤 부분이 왜 잘못되었는지**
- Step별 타임라인: 각 Step의 상태, 소요 시간
- Step별 원문:
  - 요청: Method, URL, 헤더, 바디 원문
  - 응답: 상태 코드, 헤더, 바디 원문
  - 판정 규칙별 통과/실패
  - 꺼낸 변수와 값
- 같은 케이스의 과거 실행 이력 (언제부터 실패했는지 확인)
- 제보 연결: "알려진 이슈 NH-004 (NH 확인 중)" 같은 표시. 새 실패면 "제보 등록" 버튼

### 5.4 제보 내역

- 목록 컬럼: ID, 현상 요약, 대상 API, 제보 팀, 제보일, 제보 상태, 결론, 연결 케이스의 최근 결과
- 필터: 제보 상태, 결론, 우리 팀 제보만, API
- 상세: 현상, 재현 절차, NH 답변 원문, 사용 규칙, 남은 확인 사항, 연결 케이스 실행 이력
- 상태 변경: 발견 → 제보 완료 (제보일 기록) → 답변 받음 (답변 원문·결론 입력)
- 제보 초안 복사 버튼

## 6. 비기능 요구사항

### 6.1 안전

- **실전 도메인(`api.futures.co.kr`)으로 주문·정정·취소 API 호출을 기본 차단**한다. 실전 실행은 별도 설정과 명시적 확인이 있어야만 허용한다
- 주문 케이스는 체결되지 않을 가격(지정가, 현재가와 먼 가격)과 최소 수량을 기본으로 한다
- 모든 주문 시나리오에 cleanup Step을 의무화한다

### 6.2 보안

- 앱키·시크릿은 `.env` 등 로컬 비밀 파일에 두고 git에 올리지 않는다
- 화면과 저장 기록에서 `appkey`, `appsecret`, `access_token`, 계좌번호는 마스킹한다

### 6.3 기록·확장성

- MVP 저장소는 로컬 파일 또는 SQLite. 이후 PostgreSQL 등으로 바꿀 수 있게 저장소 계층을 분리한다
- 요청/응답 원문은 그대로 보관한다 (재현·비교 목적)
- 대상 API 소스(MD, Swagger, 엑셀)와 대상 서비스(NH 외)를 추가할 때 실행기·화면 코드를 고치지 않아도 되게 한다

## 7. Claude 협업 흐름

1. 사용자가 Claude 채팅에서 요청: "domestic_order 테스트 케이스 다양하게 만들어줘"

- 케이스를 만들기 전에 제보 내역(`docs/ISSUES.md`, 이후 `issues/`)을 읽는다. 이미 제보된 현상은 새 탐색 케이스를 만들지 않고 회귀 케이스 1개만 유지한다
- NH 답변의 사용 규칙(`docs/ISSUES.md` 4장)을 지켜서 요청을 만든다

결론:

- 처음 구조는 **단일 호출 1회의 상태 코드·필드 검증**에는 맞았지만, 실제 제보의 대부분은 **응답 데이터 전체의 품질, 페이지 넘기기, 시간 흐름, 요청 값과 응답의 관계**에서 나왔다. 13건 중 문의 2건을 빼면 처음 구조로 온전히 잡을 수 있는 것은 없었다
- 위 요구사항을 추가하면 문의 2건을 뺀 11건 모두 케이스로 표현할 수 있다
- 또 하나 빠져 있던 것은 **"알려진 동작"을 관리하는 층**이다. NH 답변의 결론 대부분이 "서버는 그대로, 사용 방법을 지켜라"였다. 이 규칙을 제보 건·명세 보정·사용 규칙으로 저장하지 않으면, 같은 실패가 매번 새 실패로 보이고 같은 제보를 또 하게 된다 (4.6)
